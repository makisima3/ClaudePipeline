# AgentPipeline — инструкции для Codex

Личный канбан-трекер. Задачи из колонки «В работу» выполняет выбранный исполнитель: Claude Code через `claude -p` или Codex через `codex app-server`, по подписке без API-ключа. Пользовательское описание — в README.md, здесь только то, что нужно для работы с кодом.

## Telegram: подготовка результата и доставка

- `server/telegram.py` — общий для Claude/Codex сервис `telegram`: снимки материалов, очередь `telegram_deliveries`, один браузерный процесс за раз, состояния `prepared/pending/sending/sent/error/uncertain` и прогресс по частям. `prepared` активируется в одной транзакции со статусом задачи `done`; незавершённые черновики при старте отбрасываются. Ключ `(task_id, run_key)` (`last_run_at` либо `created_at`) предотвращает повторную доставку одного завершения. После аварии `sending` становится `uncertain`, автоматической отправки этой части нет. Подтверждённые части при повторе пропускаются.
- `tasks.telegram_notify INTEGER NOT NULL DEFAULT 0` добавляется миграцией; старые задачи не подписываются. Выбор устройства `localStorage telegram.results` определяется в браузере (телефон/планшет — включён, ПК — выключен) и передаётся при создании карточки/импорте/сообщении чата. Сервер не определяет устройство по окружению агента. `db.telegram_requested` распознаёт распространённые прямые просьбы; семантическое намерение агент чата передаёт через `telegram_notify` в MCP `create_task/update_task`. Общий выбор не меняет старые задачи.
- `finish_task` дополнен аргументами `telegram_text`, `telegram_files`, `telegram_notify`. Если задача подписана или есть явная просьба, агент готовит краткий итог (что сделано и действительно проверено) и материалы; для визуальных изменений, особенно игровых, — скриншоты, короткое видео — если нужно показать движение/взаимодействие и его реально можно записать. Успешные тесты упоминать только после реального успешного запуска. Файлы должны существовать при вызове: сервер копирует их до выхода агента. Сам агент сообщения не отправляет. Инструкция — [docs/telegram-results.md](docs/telegram-results.md).
- `tools/telegram_web.py` — опциональный Playwright/Chromium, загрузка библиотеки только в дочернем процессе. Получатель только «Избранное», id берётся из текущей авторизации и проверяется открытый peer. `login --show` — ручной вход (включая 2FA), headless `login` — QR для UI. `check` проверяет вход, `test` отправляет тест. Сырые ошибки браузера и сведения аккаунта не выводить. Зависимости устанавливаются отдельно, базовый трекер остаётся на stdlib.
- API: `GET /api/telegram`; `POST /api/telegram/check|login|test|cancel`; `GET /api/telegram/qr|instructions`; `POST /api/tasks/<id>/telegram/retry` (`resolution=received|resend` только при `uncertain`). Карточка отдаёт `telegram_delivery` с отдельной ошибкой, номером части и меткой. Обычные ошибки повторяются вручную, задача остаётся выполненной. Явное включение завершённой задачи без доставки ставит её сохранённый итог в очередь; повторное включение успешно доставленной не посылает его снова.
- `telegram_auth/telegram_error/telegram_test_at` — общие служебные настройки, запрещены для записи через обычный `POST /api/settings`. После старта ранее настроенная сессия проверяется браузером заново. Профиль сам по себе не означает готовность. `main.py` запускает `telegram.loop`, передаёт callbacks состояния/активных задач/перезапуска. Доставка ждёт отсутствия задачи в `orch.runs`; активная операция входит в `active_runs()`, новые при отложенном перезапуске не начинаются. `kill()` гасит дерево дочернего процесса. Боевой сервер руками не перезапускать.
- Локально вне git: `data/telegram/profile/` (авторизация), `results/<token>/` (снимки), `qr.png/qr-next.png` (временный QR), `job.json` (временное задание). Очередь и прогресс — в `data/tracker.db`, пути к снимкам относительные к `data/telegram/`. Текущий QR и job удаляются после операции; QR также при перезапуске. Не копировать в репозиторий личный профиль/данные старого tgSend, не зависеть от его путей или aliases.
- Проверки: `tests/test_telegram.py` — отдельная база и заглушки транспорта/агентов, `tests/ui_check.py` — новые устройства/ручной выбор/карточка/явная просьба/повтор на 390 и 1280 px. Реальные проверки разрешены только в «Избранное» настроенного аккаунта. Claude для проверок не запускать.

## Устройство

- `server/git_readiness.py` — `check(path, mode, auth)`: диагностика предпосылок Git проекта без изменения конфигурации, коммитов, push, вызова credential helpers и обращения к remote. `GET /api/projects/<id>/git-readiness?mode=off|commit|commit_push&auth=existing|gh` в `main.py` проверяет параметры и берёт папку из БД. `off` не вызывает команды, `commit` не требует remote/авторизации. Для push учитываются `branch.*.pushRemote`, `remote.pushDefault`, remote ветки, pushURL и `push.default`; сложные refspec/mirror и несколько адресов требуют ручной проверки. `gh auth status --active --hostname` вызывается только при выбранном `auth=gh` и одном HTTPS-адресе; его вывод отбрасывается. URL/автор/сырой вывод ошибок не возвращаются в UI/логи. `status=local_ready` означает только предпосылки, `write_access=not_checked` всегда; ошибки реального push агент сохраняет в отчёте без секретов и без обхода отказов. Панель в настройках (`gitReadinessPanel`, `checkGitReadiness`) и `App.openGitSettings(projectId)` — общий вход для настроек и мастера первого запуска; способ проверки хранится только в localStorage `gitAuth.<pid>` и не настраивает Git. Проверки — `tests/test_git_readiness.py`, без реального push.
- `server/runtime.py` — `AGENT`/`NAME`, выбор из `--agent` или `PIPELINE_AGENT` (по умолчанию claude); файловая блокировка `data/server.lock` до импорта db при запуске main.py. Одна база — один сервер независимо от порта; `--after` ждёт освобождения блокировки. Прямые импорты модулей блокировку не берут и допустимы только в тестовой копии.
- `server/codex_runner.py` — `Rpc` (JSON-RPC по stdio), `CodexRun` с теми же основными колбэками, что ClaudeRun, плюс `on_session`; реальный id сохраняется до начала хода. `preflight` проверяет CLI >= 0.166.0, вход ChatGPT и получает модели через model/list. Закреплены forced_login_method=chatgpt и model_provider=openai. Запросы разрешений передаются в существующие approve/approve_status; обычные вопросы — через tracker.ask_user. Фильтровать события по threadId/turnId. `generate` — временные read-only сессии, без MCP, shell и apps; любые разрешения отклоняются. `ACTIVE` учитывает также служебные генерации, чтобы перезапуск не оставлял их процессы. Логи JSONL содержат события app-server. При завершении вызывается backgroundTerminals/clean и закрывается процесс, при kill гасится дерево.
- `server/main.py` — HTTP API + SSE на `ThreadingHTTPServer`. Эндпоинты объявляются декоратором `@route("METHOD", r"/api/...")`; группы `(\d+)` приходят в обработчик как `int` после `(h, body, query)`. Ошибки — `need(cond, msg, code)` или `HttpError`. Тут же отдача статики из `web/`, `/report/<id>` → `report.html`, приём вложений чата (лимиты `MAX_*`), запуск сервера: `bind()` (с `--after <pid>` сначала ждёт выхода старого экземпляра), `spawn_successor()` для перезапуска. `Server.allow_reuse_address` в Windows выключен: иначе второй процесс молча занял бы тот же порт.
- `server/pipeline.py` — всё, что связано с логикой:
  - `Hub`/`hub` — рассылка SSE-событий (`changed`, `state`, `task_event`, `chat`/`chat_state`/`chats` — с `project_id` и `chat_id`, `questions`…);
  - промпты `TASK_SYSTEM`, `CHAT_SYSTEM`; `task_prompt`/`rerun_prompt` добавляют строку `git_line()` с режимом настройки `git_mode` (`GIT_MODES`: `off`/`commit`/`commit_push`), правило коммита — в `TASK_SYSTEM`;
  - `Orchestrator`/`orch` — цикл `tick()` раз в 1,5 с, лимит `max_parallel`, в одном проекте одна задача за раз, пауза по лимиту подписки (`pause_until`), `recover()` после рестарта;
  - `finish_task`, `answer_question`, `on_manual_move`;
  - `Chat`/`chat` — чаты проекта: `runs` по `chat_id`, у каждого чата своя сессия Claude (`chats.session_id`, продолжение через `--resume`). Отвечать одновременно могут разные чаты, в одном чате — один ответ за раз. `create` (пустой безымянный чат проекта не плодит, отдаёт его), `rename`, `send` (название из первого сообщения — `chat_title`, до `CHAT_TITLE_LEN` символов), `stop`, `stop_project`, `delete` (сообщения и папка вложений чата). Сообщение в удалённый чат `db.add_chat` молча не пишет: ответ, прерванный удалением, никуда не попадает. `rename` ставит `title_kind='manual'`, `retitle` («Придумать название заново», ✨) сбрасывает его и ставит в очередь `titler`;
  - `Titler`/`titler` — автоназвания чатов: очередь и поток `loop()` (запускается из `main.py`), по одному `claude -p` за раз (`generate`: `--model haiku --tools "" --setting-sources "" --system-prompt TITLE_SYSTEM --strict-mcp-config --no-session-persistence`, cwd — временная папка, чтобы не грузить CLAUDE.md; таймаут `TITLE_TIMEOUT`). Вход — `dialog()`: первые сообщения user/assistant, до `TITLE_INPUT` символов; пусто, пока Claude не ответил. Запрос ставится из `Chat._done`, пока `title_kind IS NULL` (то есть до первого удачного названия), результат пишется только если чат за это время не переименовали руками. Ошибка — в консоль `[title]`, название остаётся. `_backfill()` при старте разбирает `legacy`: совпадает с `chat_title` первого сообщения или «Чат от …» — в очередь, иначе `manual`. `chat.info()` отдаёт флаг `titling`, начало и конец генерации — SSE `chats`;
  - `Restart`/`restart` — отложенный перезапуск сервера (см. ниже), `BOOT_ID` — id текущего запуска, `log_restart` пишет в `data/restart.log`;
  - `links_block`/`link_info` — раздел «Связанные задачи» в `task_prompt`/`rerun_prompt` (колонка, статус, `summary`, путь к отчёту, если файл есть); `changed_links(pid, ids)` — `changed` для проектов обеих сторон связи;
  - `mcp_call`/`_mcp` — обработчики всех MCP-инструментов;
  - `import_parse` — разбор текста в задачи через `claude -p --json-schema`.
- `server/runner.py` — `ClaudeRun`: собирает команду `claude -p --output-format stream-json`, пишет MCP-конфиг в `data/runs/mcp/<key>.json`, читает stream-json в фоновом потоке и зовёт колбэки `on_text/on_tool/on_rate_limit/on_done` (`on_done` ровно один раз). `claude -p` не выходит, пока живы его фоновые Bash/PowerShell-задачи, и по их завершении сам начинает новый ход, поэтому после `result` даётся `EXIT_GRACE` секунд на выход (новый `system/init` сбрасывает отсчёт), потом дерево гасится `_kill_tree()` (`taskkill /T /F`), а в `on_done` уходит последний result с `reaped=True`. `killed=True` — только ручной `kill()`. Первая строка лога каждого запуска — `{"type": "pipeline_prompt", "resume", "prompt"}`: что ушло агенту на вход. Здесь же `PORT` из `PIPELINE_PORT`.
- `server/updater.py` — обновление с GitHub: `Updater`/`updater`. `loop()` (поток из `main.py`) при старте и раз в `update_check_minutes` минут (0 — только вручную) делает `check()`: `git fetch origin main` и сравнение `HEAD` с `origin/main` (позади/впереди, до 50 заголовков новых коммитов). Состояние в памяти (`updater.state()`, оно же `update` в `/api/state`), каждое изменение — SSE `update`. `update()`: fetch → `blockers()` (ветка не `main`, `git status --porcelain` не пуст, свои коммиты впереди — отказ с причиной) → `git pull --ff-only origin main` → `compile()` всех `server/*.py` (не компилируется — перезапуск отменяется) → `restart.request()`. Только fast-forward: никаких reset/stash/force. `git()` — без окна, с таймаутом, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, `LC_ALL=C` (английский вывод для `HINTS`); ошибки — `GitError` с понятным текстом, в UI их видно тихо в настройках.
- `server/mcp_tracker.py` — stdio MCP-сервер, который запускает сам Claude Code. Тонкая прослойка: набор инструментов зависит от роли (`TASK_TOOLS` для `task`, `CHAT_TOOLS` для `chat`), каждый вызов уходит в `POST /api/mcp/call`. Исключение — `approve`: он сам опрашивает `approve_status`, пока пользователь не ответит. `create_task` (обе роли) принимает `links` — id связанных задач; `get_task` (обе роли) отдаёт `links` с итогами и путями к отчётам; `update_task` (chat) — `links` добавить, `unlink` убрать.
- `server/db.py` — SQLite `data/tracker.db` (WAL, один connection под `RLock`). Хелперы `q/one/ex`, схема в `SCHEMA`, настройки по умолчанию в `DEFAULT_SETTINGS`, системные колонки в `SYSTEM_COLUMNS`.
- `web/` — чистые HTML/CSS/JS без сборки и фреймворков: `index.html` + `app.js` (вся SPA), `md.js` (свой рендер markdown), `report.html` (страница отчёта), `style.css`. `app.js` и страница отчёта задают `html[data-agent]` по `agent` из `/api/state`: Codex всегда использует тёмную графитовую палитру, Claude — прежнюю палитру с учётом системной темы. Цвета и состояния общих компонентов задаются CSS-переменными; модель задачи на тему не влияет.
- `docs/screenshots/` — скриншоты для README. Снимать только на демо-данных (копия трекера во временной папке на другом порту + headless Edge `--screenshot --virtual-time-budget`), не на боевой базе. В копии подключить перед `app.js` вспомогательный скрипт: он подменяет `EventSource` заглушкой (с открытым SSE headless Edge не дожидается конца загрузки), открывает нужный экран по параметрам URL и подставляет ответ импорта. `recover()` при старте копии переводит `running` в `resume` и отменяет запросы прав — такие данные править в базе после старта. Плашку обновления даёт временный клон с bare-репозиторием в роли `origin`, в котором есть новые коммиты.

## Схема БД (кратко)

`settings(key, value)`, `projects` (path — рабочая папка Claude, `chat_session_id`), `columns` (`kind`: backlog/todo/progress/waiting/done у системных, NULL у своих), `tasks` (`status`, `session_id`, `pending_prompt`, `summary`, `report_path`, `cost_usd`…), `events` (лента задачи), `questions` (`kind`: question/permission), `chats` (`title` — NULL, пока не было первого сообщения; `title_kind` — NULL временное из первого сообщения / `auto` от модели / `manual` / `legacy` у чатов до автоназваний; `session_id`; `updated_at` — время последнего сообщения; id `AUTOINCREMENT`, чтобы id удалённого чата не достался новому), `chat_messages` (`chat_id`, `attachments` — JSON), `task_links(task_id, linked_id, created_at)` — связь задач, двусторонняя и хранится одной строкой с `task_id < linked_id` (PK от дублей, `ON DELETE CASCADE` с обеих сторон; хелперы `db.task_links/link_tasks/unlink_tasks`). Связи между проектами разрешены. `projects.chat_session_id` устарел: при старте `db._migrate_chats()` переносит старую переписку проекта (сообщения без `chat_id` и `chat_session_id`) в чат «Чат от <дата>», а вложения — из `data/uploads/<pid>/` в `data/uploads/<pid>/<chat_id>/`.

Статусы задачи: `idle`, `queued`, `running`, `resume` (продолжить с `pending_prompt`), `waiting`, `done`, `error`, `interrupted`.

Миграции: новые таблицы — через `CREATE TABLE IF NOT EXISTS` в `SCHEMA`; новые колонки — через `ALTER TABLE` в блоке «миграции старых баз» в `db.py` (база пользователя уже существует).

## Поток данных

1. Карточка попадает в колонку `todo` → `status='queued'`.
2. `orch.tick()` берёт её (сначала `resume`, потом `todo` по позиции) → `start_task` переносит в `progress`, `status='running'`, создаёт `agent_run` (ClaudeRun/CodexRun) с `cwd` = папка проекта (отсюда подхватывается CLAUDE.md или AGENTS.md выбранного агента).
3. `runner` запускает `claude -p` с `--mcp-config` → Claude Code поднимает `mcp_tracker.py` с env `PIPELINE_URL/ROLE/TASK_ID/PROJECT_ID`.
4. Вызовы `mcp__tracker__*` → `POST /api/mcp/call` → `pipeline._mcp`. `ask_user` переводит задачу в `waiting`; ответ пользователя → `status='resume'` → продолжение через `--resume <session_id>`. `finish_task` пишет отчёт и переносит в `done`.
5. Пока `_done` разбирает итог хода, задача остаётся в `orch.runs` (всё под `orch.lock`, как и `answer_question`), так что продолжение после ответа стартует только когда прошлый процесс завершён (самое позднее через `EXIT_GRACE` после `result`).
6. Перезапуск: `POST /api/restart` (кнопка в настройках) или MCP `restart_tracker` (роли task и chat) ставят `restart.since`. С этого момента `tick()` не берёт задачи, чат отвечает 409, в `orch.state()["restart"]` видно, сколько запусков ждём. `restart.check()` в цикле оркестратора ждёт, пока опустеют `orch.runs` и `chat.runs` (не дольше `RESTART_TIMEOUT` = 10 мин, потом `kill()` — задачи уйдут в `resume`), шлёт SSE `restarting` и вызывает `restart.exit` из `main.py`. Тот запускает новый экземпляр (`python main.py --no-browser --after <pid>`, `CREATE_NEW_CONSOLE`, свёрнутое окно, по возможности вне job-объекта) и гасит старый (`srv.shutdown()` → `os._exit(0)`). Новый ждёт выхода старого, занимает порт и делает `recover()`.
7. Связанные задачи: `GET /api/tasks/<id>` отдаёт `links` (id, заголовок, статус, колонка, проект), `POST /api/tasks/<id>/links` `{task_id}` — связать, `DELETE /api/tasks/<id>/links/<other>` — убрать, `GET /api/tasks?q=&exclude=` — поиск для связи по номеру или части заголовка во всех проектах. На доске у задачи поле `links` — число связей.
8. Обновление: `GET /api/update` (состояние), `POST /api/update/check` (проверить сейчас, синхронно), `POST /api/update` (обновить; отказ — 409 с причиной, она же в `update_error`). После pull перезапуск идёт по п. 6, плашка `#updbar` под шапкой показывает «Обновлено, перезапуск после завершения текущих задач…»; новая страница грузится по смене `boot_id`, миграции БД применяет `db.py` при старте. Кнопка «Позже» прячет плашку до следующего `origin/main` (`localStorage.updHidden`).
9. Чат: `GET/POST /api/projects/<pid>/chats` (список с флагом `running` / новый), `PATCH/DELETE /api/chats/<id>` (переименовать / удалить), `POST /api/chats/<id>/title` (придумать название заново; 400, если Claude ещё не ответил), `GET/POST /api/chats/<id>/messages` (история / отправить), `POST /api/chats/<id>/stop`, файл вложения — `GET /api/chat/<message_id>/files/<n>`. В браузере открыт один чат (`S.chat`), список — `S.chats`; событие `chat` применяется только к открытому чату с тем же `chat_id`, `chats` перечитывает список. Последний открытый чат проекта — `localStorage` `chat.<pid>`.
10. Изменения уходят в браузер через `GET /api/events` (SSE), клиент перечитывает нужные данные. Сервер слушает одна вкладка (держит Web Lock `agentpipeline-events`) и пересылает события остальным через `BroadcastChannel`. Иначе каждая вкладка держала бы своё соединение, а по HTTP/1.1 их ~6 на хост. Если очередь клиента в `Hub` переполнилась, `/api/events` обрывает поток. После (пере)подключения все вкладки делают `resync(true)`. Первое событие потока — `hello` с `boot_id` (он же есть в `/api/state`); если он отличается от запомненного при загрузке, вкладка делает `location.reload()`. Пока связи нет, висит плашка `#offline` («Трекер перезапускается…» или «Нет связи…»). Видимая вкладка сверяется с сервером раз в 20 с и при фокусе. В `app.js` ответы `loadBoard/loadState/refreshTask/renderQuestions/loadChats/openChat` проходят через `fresh(key)`: ответ, после которого ушёл более новый запрос того же вида, отбрасывается. Пока открыт не «Доска», события доску не перечитывают, поэтому `setView("board")` загружает её заново.

Где что лежит (`data/` в `.gitignore`):
- `data/tracker.db` — база;
- `data/reports/task-<id>.md` — отчёты (прошлый отчёт сворачивается в `<details>`);
- `data/runs/task-<id>.jsonl`, `chat-<pid>-<chat_id>.jsonl` — сырые логи stream-json;
- `data/runs/mcp/` — MCP-конфиги запусков;
- `data/uploads/<project_id>/<chat_id>/` — вложения чата (удаляются вместе с чатом или проектом);
- `data/restart.log` — журнал перезапусков (кто запросил, когда, pid старого и нового экземпляра, ошибки) и обновлений (`запрошен (обновление <старый> -> <новый>)`).

Транскрипты сессий — у самого Claude Code в `~/.claude/projects/<папка>/<session_id>.jsonl` (`pipeline.transcript_path`).

## Запуск и проверка

- `start_claude.cmd` / `start_codex.cmd` → `python server\main.py --agent claude|codex`, открывает http://127.0.0.1:8765. Флаг `--no-browser` — без браузера. Порт — переменная `PIPELINE_PORT`.
- Сервер, скорее всего, уже запущен, и ты работаешь внутри него. **Не перезапускай и не останавливай его руками** — это прервёт твою же сессию. Второй экземпляр из этой папки на другом порту тоже не поднимай: он делит `data/tracker.db`, выполнит `recover()` и начнёт брать те же задачи (для проверок — копия во временной папке на другом порту).
- **Изменения в `server/` вступают в силу только после перезапуска.** Если задача меняла `server/`, после `finish_task` вызови `mcp__tracker__restart_tracker`: трекер перезапустится сам, когда твой процесс завершится, и страница перезагрузится. В отчёте напиши, что перезапуск запрошен. Изменения только в `web/` перезапуска не требуют.
- Проверка без запуска: `python -m py_compile server/*.py`. Отдельные функции можно проверять импортом модулей во временной копии проекта (иначе `db.py` откроет боевую базу). `web/` перечитывается браузером без кэша (`Cache-Control: no-cache`).
- `python -m unittest discover -s tests -v` — автоматические тесты без моделей; сами создают отдельную копию и старую схему базы для проверки миграций.
- `python tests/ui_check.py` — необязательная проверка DOM и скриншотов Edge (390/1280 px), без моделей, для запуска нужны Edge и Node 22+.
- `python tests/live_codex.py` — реальные короткие проверки Codex в отдельной копии (расходуют подписку). Рабочую базу не используют. Claude в рамках этой задачи не запускать, проверять только код и заглушки.
- `node --check web/app.js` — необязательная проверка синтаксиса JS, Node не нужен для работы трекера.
- Репозиторий https://github.com/makisima3/AgentPipeline (ветка `main`, `gh` залогинен), лицензия MIT. Пушит только владелец, остальные — Issues и PR из форка (`CONTRIBUTING.md`, шаблоны в `.github/`). В git только код, README, CLAUDE.md, `CONTRIBUTING.md`, `LICENSE`, `.github/` и `docs/`; `data/` и личные данные не коммитить.
- **Коммит на задачу** (любой проект трекера с git, режим — настройка `git_mode`, приходит строкой «Git: …» в промпте задачи): в начале посмотреть `git status`; в конце, перед `finish_task`, закоммитить ТОЛЬКО изменения своей задачи с сообщением `#<id> <заголовок>` + 2–5 строк, что сделано. Не связанные изменения — отдельными коммитами, файлы добавлять явно (общий файл — `git diff` → свой патч → `git apply --cached`). Чужие незакоммиченные изменения не трогать и не включать, упомянуть в отчёте. В режиме `commit_push` — `git push` без force; если не прошёл, не обходить (без force/rebase/reset), написать в отчёте. `off` или не git-репозиторий — git не трогать.

## Соглашения

- Базовый трекер: только stdlib Python 3.10+, без pip и npm, без CDN во фронте. Исключение — опциональный транспорт Telegram: Playwright и Chromium устанавливаются отдельно и не импортируются базовым сервером.
- Тексты UI, ошибки API, промпты, комментарии в коде и общение — на русском.
- Стиль как в соседних файлах: короткие функции, плотный код, комментарии редкие и по делу, docstring в одну строку.
- Новый MCP-инструмент: схема в `mcp_tracker.py` (в нужный список роли) + ветка в `pipeline._mcp`.
- Новая настройка: ключ в `db.DEFAULT_SETTINGS` (иначе `POST /api/settings` её проигнорирует) + поле в UI.
- После изменения данных на доске вызывай `changed(project_id)` из `pipeline.py` (в `main.py` — `pl.changed`), чтобы обновился браузер.

## Первое знакомство и настройка

- При добавлении или изменении функций оценивай влияние на первое знакомство и настройку. Если меняются обязательные условия, авторизация, интеграции или ключевой сценарий пользователя, обновляй соответствующие шаги мастера и README в той же задаче. Актуализация условная, по влиянию на пользовательский путь: мелкие внутренние правки не требуют нового шага или повторного обучения.
- Мастер — три шага в `web/app.js` (`openOnboarding/renderOnboarding`), стили в `web/style.css`, неблокирующее предложение `#welcome` в `web/index.html`. Git использует общие `gitReadinessPanel/checkGitReadiness/openGitSettings`, Telegram — `/api/telegram` и `openTelegramSettings`; отдельного входа в мастере нет. При просмотре модели не запускаются.
- `settings.onboarding_status` — общий для установки и обоих исполнителей: `pending` по умолчанию (включая старые базы), `completed` или `skipped`. `POST /api/settings` принимает только два конечных значения, `/api/state` отдаёт сохранённое. Перезапуск, обновление, новое устройство и повторное открытие не сбрасывают выбор. Пока выбор не сделан, доска доступна рядом с предложением. Статусы интеграций запрашиваются заново; прохождение мастера не означает подключения.
- Проверки: `tests/test_onboarding.py` — новая/старая база, валидация, сохранение в новом процессе и смена исполнителя; `tests/ui_check.py` — шаги, общие настройки, пропуск/завершение, новое устройство и скриншоты 390/1280 px без реальных моделей и авторизаций.

## Разделение исполнителей

`pipeline.agent_run` выбирает реализацию, `preflight` для Codex выполняется до recover/потоков. `/api/state` отдаёт agent, agent_name, agent_info (каталог моделей и версия). Выбор исполнителя фиксирован на процесс, меняется стартовым файлом; spawn_successor передаёт его явно.

Старые tasks/chats.session_id и tasks.model/effort принадлежат Claude. Новые codex_session_id, codex_model, codex_effort — Codex, last_provider — последний успешно отработавший исполнитель. Миграции добавляют колонки без удаления данных. db.agent_row/get_task/get_chat проецируют поля выбранного агента; db.update_task и set_chat_session записывают только его поля. Не обновлять last_provider при неудачном старте: повторная попытка должна снова получить контекст другого исполнителя. При смене в промпт добавляется доступный контекст задачи/чата; чужой session_id никогда не используется для resume.

Настройки model, effort, chat_model, permission_mode, pause_until, pause_estimated разделены префиксом codex_ в SQLite; db.get_settings/get_setting/set_setting прозрачно выбирают нужные. Остальные настройки и сама доска общие. Не записывать в cost_usd стоимость Codex: нет достоверного эквивалента API; UI скрывает её в режиме Codex. При неизвестном сбросе лимита pause_estimated помечает время следующей попытки. Codex-транскрипт ищется по реальному id в CODEX_HOME/sessions, если файла нет — не выдавать выдуманный путь.

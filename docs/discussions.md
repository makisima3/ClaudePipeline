# Обсуждение готового результата

На сайте и в Android у результата есть **Обсудить**. Открывается последний выбранный доступный чат этого проекта (иначе самый свежий); только если чатов нет, создаётся обычный пустой чат. Отдельного чата на каждую задачу нет. Нажатие прикрепляет результат к следующему сообщению, сохраняет набранный текст/файлы и ничего не отправляет. Над вводом видны проект, локальный номер, заголовок, время завершения, ссылки на карточку и конкретный результат. Крестик убирает прикрепление. Повторное нажатие для того же результата безопасно; замена другого прикрепления требует явного выбора.

После отправки плашка остаётся в истории сообщения. Агент получает серверный снимок описания, статуса завершения, итога, полного отчёта и материалов с глобальным `task_id`, `result_id`, `run_key`. Следующее сообщение в этом диалоге получает последний прикреплённый контекст повторно, в том числе при продолжении или смене исполнителя Claude/Codex. Другая прикреплённая запись меняет предмет обсуждения. Снятие прикрепления из черновика отменяет его добавление к следующему сообщению; уже отправленная история чата сохраняется.

Пример: «Кнопки мелкие, создай задачу на увеличение». По просьбе агент создаёт продолжение с исходным глобальным ID в `links`; связь видна в обеих карточках. При обычном обсуждении новая задача не создаётся. Выполненная исходная карточка не меняется. Флаг Telegram новой задачи берётся из настройки устройства в отправляемом сообщении или явной просьбы, а не из исходной задачи. Правило создания продолжения передаётся агенту в промпте и использует прежний API связей.

## Черновики и ошибки

Черновик хранится локально в IndexedDB с файлами `File`; ключ — `installation_id/project_id/project_created_at/chat_id`, с временным `new` до создания первого чата. Время создания проекта защищает от повторного использования его ID. Переключение проекта/чата и перезагрузка восстанавливают свой черновик. У сайта и WebView отдельные локальные черновики; отправленная история общая на сервере. Очистка данных браузера/приложения удалит местные черновики. При недоступности IndexedDB остаются память текущей страницы и текстовый резерв localStorage; UI предупреждает о риске потери файлов, а отсутствие восстановленных файлов требует повторного прикрепления или явного продолжения без них.

Запрос отправки имеет сохранённый `client_request_id`. До квитанции редактор защищён от изменения; при обрыве текст, файлы и привязка остаются, кнопка отправки повторяет тот же запрос. Сервер под замком возвращает квитанцию ранее принятого сообщения без повторной записи, загрузки файлов и запуска агента. После подтверждения черновик очищается. Если файлы неопределённой отправки не восстановились, сначала проверяется только квитанция (`receipt_only`), без отправки неполного сообщения. Известная ошибка 4xx разблокирует редактор. Пустое прикрепление само по себе не отправляется.

Если карточка удалена, сохранённый результат можно обсудить, но связать новую задачу с удалённой нельзя. Повторное использование технического ID другой карточкой не создаёт ложную связь: проверяются проект и локальный номер. Недоступный/чужой результат отклоняется до сохранения файлов и запуска агента; текст остаётся в черновике, прикрепление можно снять. Исторический снимок сообщения остаётся при исчезновении результата. Отсутствие локального файла отчёта не мешает передать полный текст отчёта. Недоступные материалы агент должен обозначать явно.

## API и схема

`POST /api/chats/<chat_id>/messages` сохраняет прежние `text`, `attachments`, `telegram_notify` и принимает:

```json
{
  "text": "Кнопки мелкие, создай задачу на увеличение",
  "attachments": [],
  "telegram_notify": true,
  "task_context": {"task_id": 26, "result_id": 15},
  "client_request_id": "f8aac4b5-a7ef-4658-9f5c-3fe2718d15a2"
}
```

Оба ID — глобальные технические ключи, не отображаемый номер задачи. Сервер проверяет соответствие результата исходной задаче и проекту чата. Клиентские заголовки/итоги не принимаются как контекст. Без `task_context` и `client_request_id` прежние клиенты продолжают работать. Квитанция — `{"ok":true}`; повтор — также `duplicate:true,message_id`. `receipt_only:true` с тем же ключом возвращает только существующую квитанцию либо 409, не создавая сообщения. Ключ повторной отправки принадлежит чату и не должен использоваться для другого сообщения.

- `chat_messages.task_context TEXT NULL` — JSON серверного снимка с `task_id`, `result_id`, `run_key`, проектом/номером/заголовком, временем, описанием, статусом, итогом, текстом, полным отчётом, его локальным путём и файлами с локальными путями/API URL. Это намеренно не FK: снимок переживает удаление карточки/результата.
- `chat_messages.client_request_id TEXT NULL` и уникальный частичный индекс `(chat_id, client_request_id)` — идемпотентность. GET истории и SSE `chat` возвращают эти поля; JSON контекста разобран в объект, отсутствующий — `null`.
- `task_results.description/status TEXT NULL` — снимок для новых завершений. Старые записи остаются `NULL`: их историческое описание/статус не восстанавливаются из изменённой карточки. Публичный результат дополнительно отдаёт `source_task_id` и `run_key`, включая удалённую карточку.
- `data/results/reports/result-<result_id>.md` — доступный агенту отчёт именно этого результата, извлечённый из неизменяемого снимка БД при прикреплении. Изменяемый `data/reports/task-<id>.md` для обсуждения не используется.
- `server/discussions.py` — проверка адресов, снимок и промпт; `web/discussions.js` — черновики, плашки и переход из общей ленты. Зависимости сервера остаются stdlib.

Миграция добавляет поля/индекс без переписывания прежних сообщений и результатов. Новых настроек или обязательных условий нет; мастер первого запуска не меняется. Нативный APK 1.0 загружает эти экраны с сервера, пересборка и новый релиз для этой функции не нужны.

## Проверки

`python -m unittest discover -s tests -v` включает `tests/test_discussions.py`: оба исполнителя с заглушками, новая/продолжаемая сессия и смена исполнителя, точный старый результат после повторного запуска, валидация проекта и одинаковых локальных номеров, конкурентные повторы, файлы, сохранение в новом процессе, удалённая/замещённая карточка, старые поля NULL, отсутствие локального отчёта и двусторонние links.

Для UI запустите `python tests/android_demo.py`, возьмите порт из `output/playwright/task-24/demo.json`, откройте через Playwright CLI/Edge и выполните `run-code --filename tests/discussions_ui.js`. Скрипт использует отдельную временную копию, настоящие UI/HTTP/IndexedDB, заглушку модели и штатный MCP для создания связи; проверяет 390/1280 px, файлы после перезагрузки, смену чатов/проектов, повтор, снятие, потерю квитанции и офлайн. Скриншоты сохраняются в `output/playwright/task-26/`.

`python tests/android_discussions_check.py --adb <adb>` работает только на эмуляторе с установленным APK и тем же демо-сервером. Проверяет реальный переход, клавиатуру, системную «Назад», перезагрузку черновика, отправку со структурированной привязкой, ответ заглушки, связанную задачу и историю после перезапуска приложения. Реальные модели и Telegram не запускаются. После проверок остановите свои демо-сервер/эмулятор/браузер.

Дополнительные UI-проверки: `run-code --filename tests/discussions_edges_ui.js` — замена/отмена прикрепления, устаревший результат без потери текста, удалённая карточка, первый чат и двойное нажатие. Для обеих веток confirm в этом скрипте подставлено решение, системный confirm отдельно проверяется в APK.

Явная проверка по подписке: `python tests/live_discussions_codex.py` — настоящий Codex в отдельной временной копии, два хода одной сессии: чтение исторического описания/отчёта/материала и создание связанной задачи только по просьбе с текущим флагом Telegram. Claude и реальная доставка не запускаются; в обычный unittest этот тест не входит.

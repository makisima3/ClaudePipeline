# Android и общая история результатов

AgentPipeline для Android — устанавливаемый APK (Android 8.0+, API 26; актуальный Android System WebView). Это клиент существующего сервера: проекты, задачи, вопросы, настройки и диалоги общие с сайтом. Приложение не запускает агентов на телефоне. Компьютер с трекером должен работать и быть доступен телефону.

## Подключение к текущему серверу

1. Обновите трекер и дождитесь штатного перезапуска. Нужен `GET /api/results/meta`, версия контракта 1.
2. Установите `AgentPipeline.apk`, разрешив установку из выбранного файлового менеджера/Telegram. Магазин приложений не используется.
3. При первом запуске введите адрес доступного сервера и нажмите **Подключиться**. Адрес проверяется до сохранения; при ошибке прежнее подключение сохраняется.

Трекер по умолчанию слушает **только `127.0.0.1:8765` на ПК**. Адрес вида `http://192.168.…:8765` сам по себе не открывает к нему доступ с телефона. Эта реализация не меняет размещение, адрес прослушивания или брандмауэр сервера.

Для подключения к нынешнему локальному серверу через USB:

```powershell
# На ПК: Android SDK Platform Tools; включите отладку USB на телефоне и подтвердите этот ПК.
adb devices
adb reverse tcp:8765 tcp:8765
```

В приложении оставьте `http://127.0.0.1:8765`. Через USB `127.0.0.1` телефона перенаправляется на ПК. После отключения кабеля, перезагрузки или переподключения ADB выполните reverse снова. При другом порте поменяйте оба номера. Авторизация ADB и установка APK на личный телефон выполняются пользователем.

Если уже есть доверенный VPN/прокси или доступный адрес сервера, укажите его полный корневой HTTP(S)-адрес без пути, логина, пароля и параметров. Используйте HTTP только через доверенное подключение: у базового трекера нет аутентификации. Не публикуйте его порт в интернете. Настройка удалённого размещения, VPN и серверной аутентификации в эту реализацию не входит.

Вверху приложения находятся **Обновить** и **Подключение**. При недоступном сервере проверьте подключение и повторите загрузку. После возврата связи интерфейс сверяется с сервером через SSE и каждые 20 секунд видимой работы. Локальная копия всей истории на телефоне не создаётся: без сети редактирование недоступно; пропущенные результаты читаются с сервера после восстановления связи.

## Результаты

В каждом проекте один системный раздел **Результаты**. Его нельзя переименовать, удалить как обычный чат или продолжить в нём диалог с агентом. Обычные чаты с агентом остаются отдельными.

Каждое завершение сохраняет номер и название задачи, текст итога, отчёт именно этого завершения и снимки переданных материалов в `data/results/`. Снимки сохраняются до выхода агента. Изображения и видео поддерживаемых форматов показываются в ленте, файлы скачиваются; в Android они попадают в **Загрузки** через системный DownloadManager. Нажатие на изображение открывает его отдельно; системная кнопка «Назад» возвращает к ленте. Выбор вложений чата использует системный файловый диалог. На телефоне есть явная кнопка отправки сообщения.

История не зависит от `telegram_notify`, подключения Telegram или исхода отправки. Позднее включение Telegram берёт сохранённый текст и материалы того же запуска. Удаление карточки задачи сохраняет результат и отчёт в ленте; **удаление проекта** удаляет его историю из базы, как и остальные данные проекта. Автоматического удаления снимков по сроку нет. Для резервного копирования нужны база `data/tracker.db` и папки `data/results/`, `data/reports/`, `data/telegram/` (для прежних доставок), `data/uploads/`. Копируйте согласованную резервную копию БД с учётом WAL, а не только открытый файл базы.

При первом обновлении доступные прежние завершённые задачи переносятся в общую историю один раз: итог и существующий отчёт, а при наличии старой доставки — её подготовленные текст и файлы. Несуществовавшие/утраченные материалы восстановить нельзя. Прежние запуски одной задачи, для которых не было отдельных сохранённых данных, не реконструируются.

Непрочитанные результаты помечены точкой в навигации и меткой **Новое**. **Всё прочитано** сохраняет позицию для текущего проекта на этом устройстве; сайт и приложение имеют независимые позиции чтения. Сама история общая. Предыдущие записи загружаются по кнопке, результаты других проектов в ленту не попадают.

## Уведомления Android

В **Подключение → Фоновая проверка всех проектов** включите проверку. На Android 13+ приложение запросит разрешение системных уведомлений. Отдельные кнопки открывают системные настройки уведомлений и батареи; отказ не блокирует работу трекера.

Используется настоящий `JobScheduler` с сетевым условием, периодом 15 минут и сохранением задания после перезагрузки. Он может запускать приложение в фоне, при закрытом экране и без открытой WebView. В видимом приложении дополнительно выполняется сверка раз в 20 секунд. Нажатие на уведомление открывает соответствующий результат и его проект, в том числе после нового запуска приложения.

**Это периодическая доставка с возможной задержкой, а не мгновенный push.** Android не гарантирует точное время: Doze, экономия заряда, ограничения производителя и недоступный сервер могут задержать уведомление на часы. После **принудительной остановки** приложение нужно открыть вручную. Обычное сворачивание и закрытие экрана разрешены. Жёсткая проверка `JobScheduler` в тестах через `cmd jobscheduler run -f` подтверждает выполнение настоящего фонового задания, но не доказывает срок автоматической доставки. [Правила JobScheduler](https://developer.android.com/reference/android/app/job/JobInfo.Builder), [Doze и ограничения сети](https://developer.android.com/training/monitoring-device-state/doze-standby).

Первое подключение начинает уведомления с текущего конца истории; прежние результаты видны в ленте без шквала старых уведомлений. Курсор привязан к сохраняемому идентификатору базы сервера, поэтому смена проекта не влияет на уведомления, а другая база по тому же адресу требует повторного подключения. После потери связи пропущенные записи читаются по возрастанию курсора, постранично. При выключенной проверке/запрещённых уведомлениях курсор не двигается: после включения придут накопившиеся новые результаты с момента первого подключения.

Ключ `(source_task_id, run_key)` исключает повторную запись одного завершения, новый запуск имеет отдельный `run_key`. Android сохраняет курсор до показа уведомления, использует постоянный ключ уведомления и `setOnlyAlertOnce`: переподключение и перезапуск не создают повторные уведомления. Между записью курсора и системным показом остаётся короткое окно: при аварийном завершении процесса уведомление может быть пропущено. Сама запись и материалы остаются в ленте. Локальная БД и системная служба Android не имеют общей транзакции; строгой гарантии exactly-once показа нет.

Внешних сервисов/ключей для этого режима не требуется. Рассматривались FCM и постоянная foreground-служба: FCM требует отдельной конфигурации проекта и сервера, а `dataSync` foreground-служба на Android 15 ограничена шестью часами за сутки и не является бессрочным каналом. Эти варианты не подменяются заглушками и не включены. [Ограничение foreground dataSync](https://developer.android.com/develop/background-work/services/fgs/timeout).

## Архитектура и сборка

Выбрана тонкая WebView-оболочка вместо отдельного нативного UI, Flutter/React Native или PWA. У отдельного UI пришлось бы дублировать все экраны и будущие функции; PWA не даёт требуемый самостоятельный устанавливаемый APK с нативным фоновым планировщиком. WebView использует **тот же `web/` с сервера**, без встроенной устаревающей копии. Бизнес-правила и данные — только в Python-сервере. При обновлении общего интерфейса APK пересобирать не нужно; изменения нативных возможностей требуют нового APK.

- `server/results.py` — подготовка, снимки, миграция доступной истории и JSON-представление.
- `task_results` — самостоятельная история; `result_meta` — идентификатор установки. Telegram не является источником новых записей.
- `/api/projects/<pid>/results?before=&after=&limit=` — лента проекта от новых к старым; `/api/results?after=&limit=` — курсор всех проектов от старых к новым. `limit` от 1 до 100, `has_more` указывает продолжение.
- `/api/results/meta` — `installation_id`, `latest_id`, `version`; `/api/results/<id>` — результат с неизменяемым отчётом; `/api/results/<id>/files/<index>` — материал (HTTP Range для видео, `?download=1` для скачивания).
- `web/results.js`, общий `web/app.js/style.css` — общие экраны; `android/src/…/MainActivity.java` — платформа, `ResultJob.java` — фоновые уведомления.
- MCP `finish_task`: **всегда** передавать `result_text/result_files`, независимо от Telegram. Прежние имена `telegram_text/telegram_files` работают как совместимые синонимы. `telegram_notify` управляет только отправкой. Оба исполнителя используют общий путь завершения.

Сборка изолирована от базового трекера. Нужны Python stdlib, JDK 17+, Android SDK Platform 36 и Build Tools 36.0.0; Gradle, npm, pip и Android Studio не обязательны. Можно явно указать уже установленный SDK Unity без его модификации:

```powershell
python android/build.py --sdk "C:/путь/к/Android/SDK" --java "C:/путь/к/JDK17"
# Либо ANDROID_HOME и JAVA_HOME, затем python android/build.py
adb install -r android/build/AgentPipeline.apk
```

Результаты: `android/build/AgentPipeline.apk` и `.apk.sha256`. Скрипт компилирует ресурсы/Java/DEX, выравнивает APK, подписывает и проверяет подпись v2/v3 и zipalign. Исходники не содержат бинарных сборочных зависимостей. Установка Android SDK и принятие его лицензии — отдельно; сервер в этом не нуждается.

Локальный ключ личной сборки создаётся в **`android/.local/signing.jks`**, пароль тестового ключа `android`. Он не включается в Git. **Сохраните этот файл для обновлений установленного приложения**: другая подпись не обновит прежний APK; удаление приложения потеряет локальные настройки/курсор/позиции чтения, но не серверную историю. Это личная сборка, не ключ для публикации в магазине. Каталог сборки и ключ игнорируются Git; готовые APK распространяются через GitHub Releases и материалы задач, в историю Git не добавляются.

## Готовый APK и следующие выпуски

**[Скачать для Android — релиз 1.0](https://github.com/makisima3/AgentPipeline/releases/tag/android-v1.0)** · [APK](https://github.com/makisima3/AgentPipeline/releases/download/android-v1.0/AgentPipeline.apk) · [SHA-256](https://github.com/makisima3/AgentPipeline/releases/download/android-v1.0/AgentPipeline.apk.sha256).

Откройте APK на телефоне, разрешите установку из выбранного браузера/файлового менеджера и установите приложение. Подключение по USB описано в начале этой инструкции. Сервер должен быть запущен отдельно из коммита `189930a7a2075ee43ca7b03b5782615b5d63ea25` или более новой совместимой версии. Общие экраны приходят с сервера и могут изменяться независимо от APK. Репозиторий и релиз публичные, для скачивания вход в GitHub не требуется.

Первый выпуск: `versionName=1.0`, `versionCode=1`, пакет `space.agentpipeline.android`, тег `android-v1.0` указывает на исходный коммит `189930a7a2075ee43ca7b03b5782615b5d63ea25`. SHA-256 APK: `f2a4ff11b884757096f01e922b28989ec160f925a22c1df96aff1337f3cd9cf8`. SHA-256 сертификата подписи: `2896d5ce0ff3cc015e6b162a6fa587c7fd817765acf4f3531ebf6c5ef64798b9`. Для проверки скачанного файла на Windows: `Get-FileHash ./AgentPipeline.apk -Algorithm SHA256`; сравните с `.sha256` из того же релиза.

Порядок выпуска без отдельной системы автосборки:

1. В `android/AndroidManifest.xml` увеличьте `versionCode` и задайте новый `versionName`. Сохраните существующий ключ подписи; перед сборкой убедитесь, что `android/.local/signing.jks` доступен, чтобы скрипт не создал другой. Не добавляйте ключ, APK и промежуточные артефакты в Git.
2. Соберите APK указанной выше командой. Проверьте подпись/zipalign, версию через `aapt2 dump badging`, SHA-256 и содержимое: никаких личных данных, приватных ключей, токенов или личного адреса сервера. Редактируемый адрес localhost для USB допустим. Проверьте сайт на 390/1280 px и установку/обновление APK поверх прошлой версии с сохранением настроек; выполните сценарии из следующего раздела. В описании отличайте реально пройденные проверки от ограничений.
3. Закоммитьте и отправьте проверенные исходники, запишите полный SHA коммита сборки. При последующих изменениях исходников APK пересобирается и проверяется заново. Сверьте `git status` и список файлов коммита: бинарников/ключей там быть не должно. Сохраните APK и `.sha256` вне Git.
4. Проверьте существующие релизы и теги: `gh release list` и `git ls-remote --tags origin`. Создайте новый тег вида `android-v<versionName>` на **коммите сборки**, не на произвольном текущем HEAD. Подготовьте UTF-8 файл заметок с изменениями, версией/коммитом, установкой/подключением, результатами проверок и ограничениями. Пример (подставьте новую версию и SHA):

   ```powershell
   gh release create android-v1.1 android/build/AgentPipeline.apk android/build/AgentPipeline.apk.sha256 --target <полный-SHA-коммита> --title "AgentPipeline для Android 1.1" --notes-file <файл-заметок.md>
   ```

   Существующий релиз/тег не перезаписывайте и не загружайте поверх него другой APK. Если выпуск уже есть, сначала проверьте его версию, коммит и хеш файла; повторная публикация не нужна.
5. Обновите ссылки/версию в README и этом разделе на новый готовый релиз. Скачайте APK по публичной ссылке без авторизации и сравните SHA-256 с локальным проверенным файлом. Для приватного репозитория явно укажите, что скачивание требует доступа к нему. Отправьте документацию в Git. Публикация в магазинах и автоматическое обновление приложения в этот порядок не входят.

## Совместное развитие и проверки

Каждая будущая общая функция и исправление должны учитывать **сайт и Android**. Общая логика/экраны меняются в `server/` и `web/`, не копируются в Android. Намеренные различия платформ документируются явно: системные уведомления, файловый диалог/DownloadManager, подключение и системная «Назад» есть в Android; сайт в этой версии не показывает системные уведомления. Позиции чтения и выбор устройства локальны.

При общих изменениях проверяйте сайт на телефоне (390 px) и ПК (1280 px), а также WebView APK: навигацию и «Назад», формы с клавиатурой, создание/изменение/перенос карточек, чат и вложения, вопросы и ответы, настройки, результаты/материалы/отчёт, переподключение. При нативных изменениях пересоберите APK и проверьте установку/обновление, отказ и выдачу разрешения, фон/выключенный экран, переход из уведомления, повторный запуск и отсутствие дублей.

```powershell
python -m unittest discover -s tests -v
python tests/ui_check.py
node --check web/app.js
node --check web/results.js
```

`tests/test_results.py` — матрица Telegram и обоих исполнителей, неизменяемые материалы/отчёт, транзакция, курсоры и пропущенные записи, восстановление в новом процессе, изоляция и удаление карточки, позднее включение Telegram, HTTP Range. Транспорт/модели — заглушки.

`python tests/android_demo.py` поднимает демо-копию на случайном localhost-порту, пишет её адрес в `output/playwright/task-24/demo.json`. Боевой сервер/база не используются: циклы оркестратора/транспорта не запускаются, ответы чата заменены заглушкой `DemoRun`, модели не вызываются. Через `adb reverse tcp:8765 tcp:<демо-порт>` можно проверить установленный APK. После подключения и выдачи разрешения `python tests/android_check.py --adb <путь-к-adb>` проверяет экран/фон, потерю подключения, повторы, перезапуск процесса, клик отдельного уведомления и «Назад». Дополнительный `--reboot-only` действительно перезагружает **только эмулятор** и проверяет сохранённое задание/курсор без запуска Activity. Скрипт отказывается работать на физическом телефоне.

Для UI ленты откройте демо-адрес через `playwright-cli open http://127.0.0.1:<демо-порт> --browser=msedge`, затем `playwright-cli run-code` с содержимым `tests/results_ui.js` (PowerShell: `(Get-Content tests/results_ui.js -Raw -Encoding UTF8)`). Playwright CLI — необязательный инструмент проверки; допустим запуск через `npx --yes --package @playwright/cli playwright-cli`. Проверяются изображения, настоящее воспроизведение видео, скачивание, непрочитанное, отчёт, проекты, офлайн/перезагрузка, 390/1280 px и прямая ссылка.

Остановите демо-сервер и эмулятор после проверки. Скриншоты снимайте только на демо-данных. Успешными в отчётах называйте только реально выполненные проверки; отдельно различайте принудительный тест задания и наблюдение естественного фонового расписания.
